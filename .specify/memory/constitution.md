# MoveDemo 專案憲章 (Constitution)

## 核心原則

- 使用正體中文編寫與回答

### I. 物件導向完整性 (程式碼品質)
維持清晰的物件導向設計，針對節點 (Node)、空間 (Space) 與策略 (Strategy) 使用明確的抽象化。邏輯必須模組化並遵循單一職責原則 (SRP)，以利於遊戲變體與求解演算法的擴充。避免產生程序式的「上帝物件 (God Objects)」。

### II. 驗證驅動 (測試標準)
所有的演算法邏輯與求解策略「必須」通過 JUnit 測試進行實證驗證。正確性嚴格依據理論最小步數公式進行衡量：`步數 = N * (N + 2)`。未通過這些驗證關卡的策略不被視為「完成」。

### III. CLI 優先的清晰度 (使用者體驗)
應用程式「必須」提供清晰、易於閱讀的 CLI 輸出，顯示解決遊戲所採取移動的確切序列。輸出格式必須保持一致，並有助於調試複雜的移動模式，特別是針對較大的問題規模。

### IV. 效能擴展性 (效能需求)
策略「應該」針對處理高達 N=26 的問題規模進行優化。記憶體管理至關重要；實作「必須」透過使用高效的狀態追蹤或剪枝技術，避免 `OutOfMemoryError` 與過長的執行時間。

### V. 模板同步化 (一致性)
透過 `.specify` 基礎設施，維持程式碼、規格說明 (Specification) 與任務 (Tasks) 之間的嚴格同步。所有新功能必須從規格說明與計畫 (Plan) 開始，且必須通過「憲章檢查 (Constitution Check)」。

## 開發標準
- **執行環境**: Java 17 或更高版本。
- **建置系統**: Gradle。
- **測試框架**: JUnit 5 (Jupiter)。
- **程式碼風格**: 標準 Java 命名慣例 (類別使用 PascalCase，方法/變數使用 camelCase)。

## 工作流程
所有新功能與錯誤修復皆須遵循 **研究 (Research) -> 策略 (Strategy) -> 執行 (Execution)** 的生命週期。
1. **研究**: 評估影響並驗證假設。
2. **策略**: 提出設計方案並進行審查。
3. **執行**: 實作並包含測試，遵循「計畫 -> 執行 -> 驗證 (Plan -> Act -> Validate)」循環。

## 治理 (Governance)
本憲章優先於所有其他本地實務。修正案需要更新版本號與相關文件。所有的 Pull Request 與實作計畫都必須驗證是否符合這些原則。
