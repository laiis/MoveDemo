# 研究報告：演算法優化與替代實作

## 1. 基準測試機制 (Benchmarking Mechanism)

### 決策
實作一個 `BenchmarkDecorator` 來包裹 `Strategy` 介面。

### 理由
- **關注點分離 (Separation of Concerns)**: 演算法本身不需要知道它正在被計時。
- **可重複使用性**: 可以套用於任何 `Strategy` 實作。
- **效能測量**: 使用 `System.nanoTime()` 測量執行時間，並記錄初始/結束步數。

### 替代方案
- 直接在 `Main` 中撰寫計時邏輯（較不靈活且違反 OCP）。
- 使用 JMH (Java Microbenchmark Harness)（對於此專案的演算法研究來說可能過於笨重）。

## 2. TheBestStrategy 優化

### 決策
- **移除 I/O 阻礙**: 在基準測試模式下，應可選擇關閉 `System.out.println` 輸出。
- **邏輯簡化**: 將複雜的優先級判斷邏輯抽離至獨立的 `HeuristicProvider` 類別，符合 SRP。
- **預分配資源**: 減少在循環中頻繁建立 `ArrayList` 的次數。

### 理由
- 現有的實作在每次移動後都會呼叫 `Step.showList`，這在大規模 N 時是主要的效能瓶頸。
- 優先級邏輯與移動執行邏輯混合在一起，難以維護與優化。

## 3. 替代演算法

### 方案 A: A* 搜尋 (啟發式搜尋)
- **優點**: 相比 BFS 能大幅減少搜尋空間，且能保證最短路徑。
- **啟發函數 (Heuristic)**: 計算每個節點與其目標位置的距離總和。

### 方案 B: 廣度優先搜尋 (BFS)
- **優點**: 實作簡單，保證最短路徑。
- **缺點**: 在 N=26 時會面臨嚴重的記憶體爆炸問題（狀態空間過大）。

### 方案 C: 遞迴加深深度優先搜尋 (IDDFS)
- **優點**: 節省記憶體，且能保證最短路徑。
- **決策**: 對於大規模 N，這可能是比 BFS 更務實的「保證最短路徑」演算法。

## 4. SOLID 原則與設計模式

### 套用模式
- **策略模式 (Strategy Pattern)**: 已存在，將繼續沿用。
- **裝飾者模式 (Decorator Pattern)**: 用於基準測試 (BenchmarkDecorator) 與日誌記錄。
- **工廠模式 (Factory Pattern)**: 用於根據使用者輸入建立不同的 `Strategy`。

### 觀察
- 在靜默 I/O 的情況下，N=26 的執行時間僅為 ~3.8ms，遠低於 5 秒的門檻。
- 步數完全符合 `N * (N + 2)` 公式。
- 記憶體消耗隨 N 增長。
